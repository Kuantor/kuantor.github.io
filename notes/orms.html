1Two models that disagree

Video: slide 3

A relational database and a Python program describe the same data in two different models, and they disagree on more points than the video had time for:

The relational modelThe object model
TablesClasses
RowsInstances
ColumnsAttributes
Foreign keys, followed with a joinReferences, followed with a dot: article.author
No inheritanceInheritance hierarchies
Identity by primary keyIdentity by memory address
Set-based operationsIteration

The name, object-relational impedance mismatch, comes from electrical engineering. Connect two circuits of different impedance, and part of the signal is reflected back at the junction instead of passing through. Both models are coherent on their own; the cost is at the junction. An ORM is the adapter you put there. It does not remove the mismatch. It moves it somewhere you can manage. The term dates from the object-database debates of the 1990s, and the electrical metaphor is the original one.

2Life without an ORM

Video: slide 4

The same job done by hand, with a database driver and nothing else:

cur.execute(
    "SELECT id, title, author_id "
    "FROM articles WHERE id = %s", (42,)
)
row = cur.fetchone()      # (42, "Hello", 7)
article = {
    "id":    row[0],
    "title": row[1],
}
  • Column order, twice. The SQL and the unpacking must agree. Add a column in the middle of the SELECT, and row[1] silently becomes the wrong field. Nothing raises.
  • No behavior. A tuple cannot validate itself and has no methods: data with the meaning taken off.
  • The author is a second query, and joining the two results is your job, every time.

None of this is wrong. Plenty of production systems are written this way, and for a small script it is the right amount of machinery. It does not scale with the number of tables, or with the number of developers touching them.

3Why Flask ships no ORM

Not in the video

Flask is a microframework: the core does routing, request handling, templating and a signed-cookie session. The ORM, forms, migrations and authentication arrive as extensions you choose, or as code you write.

DjangoFlask
Ships its own ORM; using Django means using itShips nothing: you choose, and must choose
Active Record: the model saves itself, article.save()Almost always SQLAlchemy, which is Data Mapper: plain objects, and a separate session persists them
Migrations built inAlembic, added separately

The difference between the two styles sounds academic until you try to unit-test a model without a database: with Data Mapper, the object itself knows nothing about storage.

In Flask you usually add Flask-SQLAlchemy. It does not replace SQLAlchemy; it wires it into Flask, so that every request gets one session, closed when the response is sent. That request-scoped session is the whole value of the extension, and it is the part you would otherwise get wrong.

4SQLAlchemy is two libraries: Core and ORM

Video: slide 6

Core: a SQL expression languageORM: mapping and state tracking, on top
Tables, columns, composable select()Classes mapped to tables
Compiles to each database's own dialect of SQLA session tracking what changed
No classes, no session, no objectsRelationships traversed as attributes
Set-based: fast bulk work lives hereData Mapper style, not Active Record

The two share one connection and one transaction, so you can drop from the ORM into Core in the middle of a job:

# ORM: load an object, change it, let the session write the UPDATE
article = session.get(Article, 42)
article.title = "Hello, world"
session.commit()

# Core: one set-based statement, and no objects at all
session.execute(
    update(Article).where(Article.author_id == 7).values(title="Draft")
)
session.commit()

SQLAlchemy assumes you know SQL and want leverage, not concealment. Some ORMs try to make the database invisible; this one tries to make it convenient, and when the abstraction cannot say what you mean, you drop a level instead of fighting it. Michael Bayer released it in 2006, and it has been the default for data access in Python for most of the time since.

5Declarative mapping, SQLAlchemy 2.0 style

Not in the video

class Base(DeclarativeBase):
    pass

class Author(Base):
    __tablename__ = "authors"
    id:   Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    articles: Mapped[list["Article"]] = relationship(back_populates="author")

class Article(Base):
    __tablename__ = "articles"
    id:    Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    author_id: Mapped[int] = mapped_column(ForeignKey("authors.id"))
    author: Mapped[Author] = relationship(back_populates="articles")
  • The annotation is part of the schema. Mapped[str] makes the column NOT NULL; Mapped[str | None] makes it nullable. Your type checker reads the same thing the database does.
  • relationship() is not a column. There is no such column in the table. It is the join, written once in Python: article.author and author.articles are two views of one foreign key.
  • back_populates keeps both sides in step. Append an article to author.articles, and that article's author is set in memory at once, before any SQL runs.

If a tutorial uses session.query(...), it was written before 2.0. The code still runs, but learn the 2.0 style: session.scalars(select(Article)), session.get(Article, 42).

6The session and the unit of work

Video: slide 7

  1. You change objects: session.add(a), or just article.title = "New". Nothing has been sent yet.
  2. flush() works out the INSERT, UPDATE and DELETE statements and sends them in dependency order: parents before children, so a foreign key never points at a row that does not exist yet. You did not write that order; it comes from your object graph.
  3. commit() ends the transaction, and calls flush() for you if you have not.
with Session(engine) as s, s.begin():   # commits at the end, or rolls back on an error
    s.add(Article(title="New", author_id=1))

The pattern is called Unit of Work, and so is its partner below, the Identity Map: both come from Martin Fowler's Patterns of Enterprise Application Architecture (2002). They are older than most of the frameworks that use them.

One session per request, closed when the response is sent. A long-lived session shared across requests is not a performance problem but a correctness one: it shows up as stale data, and eventually as one user seeing another user's objects.

7The identity map

Video: one sentence on slide 7

Within one session, one row is one object. Always.

a = session.get(Article, 42)
b = session.get(Article, 42)
assert a is b     # not equal: the same object

Without it, two queries touching one row would give you two copies, and changing one would not change the other. With it, there is exactly one Article 42 in the session, and everybody holds that one. Three consequences:

  • Asking again is free. session.get() for a row already loaded sends no query.
  • Objects expire on commit. Their attributes reload on the next access. Touch one after its session has closed, and you get DetachedInstanceError: the object in your hand still looks like data, but the session behind it is gone.
  • It changes how bad N+1 looks — which is the next section.

8N + 1, measured

Video: slides 8 and 9

articles = session.scalars(select(Article)).all()

for a in articles:
    print(a.title, a.author.name)

a.author reads like a.title, but the author was never loaded, so the first touch sends a query. That is lazy loading, the default for every relationship. With 100 articles by 100 different authors:

101 statements: one for the list, then one per author.

Locally, on SQLite with a hundred rows, they take a few milliseconds. Against a database across a network, at about a millisecond per round trip, the 100 extra queries add a tenth of a second to the page, and the cost grows with the data. It never crashes, which is why it survives so long.

Except when it is eleven

Same code, same 100 articles, but they share only ten authors. The script counts 11 statements, not 101. Once an author is in the session, the identity map hands back the same object without a query. So the real formula is:

1 + the number of distinct related rows, not 1 + N.

That sounds like good news, and it is the opposite. Your test fixtures have three authors and your staging data ten, so the page looks fine in development and in CI. The bug grows with production data, the one place nobody measured it. Most write-ups state N+1 as 1 + N and stop; with a session-backed ORM, the distinct-rows version is what you observe.

9Which fix, and why

Video: slide 10, and the rule it points to

Both fixes are one line on the query, and the loop does not change. Both are eager loading: you say up front which relationship you will need.

# joinedload: one query with a LEFT OUTER JOIN
select(Article).options(joinedload(Article.author))

# selectinload: the articles, then all their authors at once with WHERE id IN (...)
select(Article).options(selectinload(Article.author))

Which one to pick depends on the direction of the relationship:

DirectionUseWhy
Many-to-one
article.author		joinedloadOne author per article: the join adds columns to each row, not rows.
One-to-many
author.articles		selectinloadA join in this direction repeats the parent's columns once for every child.

Measured, statements sent and rows returned:

Loading100 articles → their authors100 authors × 50 articles each
lazy (the default)101 statements · 200 rows101 statements · 5,100 rows
joinedload1 statement · 100 rows1 statement · 5,000 rows
selectinload2 statements · 200 rows2 statements · 5,100 rows

Look at the right-hand column. The join sends one statement, but builds 100 authors out of 5,000 rows, each author's columns repeated fifty times across the network, and then thrown away in Python. That is also why SQLAlchemy makes you call .unique() on a joined collection: without it, the result raises InvalidRequestError. selectinload sends each author once and each article once. On a collection, one query is not automatically the cheaper one; what crosses the network is what costs.

10How to catch it

Video: echo=True on slide 10

You will not spot N+1 by reading code. You spot it by looking at the SQL.

  • create_engine(URL, echo=True) prints every statement. A page that scrolls hundreds of near-identical SELECTs past you has one.
  • relationship(lazy="raise"), or .options(raiseload(Article.author)) on one query, turns an accidental lazy load into an exception: 'Article.author' is not available due to lazy='raise'. Use it in tests, and N+1 becomes a failing test instead of a slow page.
  • flask-debugtoolbar shows the queries of each request in the browser: the fastest way to see that a page went from 3 queries to 300 after one innocent template change.
  • Count them yourself with the before_cursor_execute event, as the script below does. It is about ten lines.

11Migrations with Alembic

Video: one sentence on slide 11

SQLAlchemy describes a schema; it does not change a live database. That is Alembic, by the same author: versioned migration scripts, chained in order, with a table in the database (alembic_version) recording where it stands.

An alembic is a still, the copper vessel alchemists distilled in. The word came to English through Arabic al-anbīq, from the Greek ambix, a cup. Bayer named the tool as a pun on SQLAlchemy.

Autogenerate is a draft, not an answer. Alembic writes migrations by comparing your models with the live database, and it is good at it, but it guesses. It guesses wrong on renames: a renamed column comes out as a DROP followed by an ADD, correct in shape and fatal to every value in that column.

Read every generated migration before you run it, and write a rename as one: op.alter_column("articles", "title", new_column_name="headline").

Migrations are the one part of the ORM story where a mistake is not slow. It is gone.

12When an ORM is the wrong tool

Not in the video

  • The query is the point: reporting, analytics, aggregation over large tables. Clearer and faster as SQL.
  • Bulk operations: loading a million rows into objects to change one field is enormously wasteful. One set-based UPDATE in Core does it.
  • Vendor-specific features: INSERT … ON CONFLICT, window functions, CTEs, JSONB operators, full-text search. SQLAlchemy exposes many of them, but once you are fighting the abstraction to say something SQL says plainly, stop fighting.
  • A schema you do not control: a legacy database with no primary keys and mixed conventions can cost more to map than to query.

With SQLAlchemy, dropping down does not mean leaving. Core is the same library, on the same connection and in the same transaction, so the escape hatch costs nothing but the abstraction you were fighting anyway.

13Run it yourself

Every number on this page comes from this script: pip install sqlalchemy, then python n_plus_one.py. It counts what reaches the database driver, and the rows each statement returns. Checked with SQLAlchemy 2.0.51 and Python 3.14, 22 November 2026.

from sqlalchemy import ForeignKey, create_engine, event, select
from sqlalchemy.orm import (DeclarativeBase, Mapped, Session, joinedload, mapped_column,
                            relationship, selectinload)


class Base(DeclarativeBase):
    pass


class Author(Base):
    __tablename__ = "authors"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    articles: Mapped[list["Article"]] = relationship(back_populates="author")


class Article(Base):
    __tablename__ = "articles"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    author_id: Mapped[int] = mapped_column(ForeignKey("authors.id"))
    author: Mapped[Author] = relationship(back_populates="articles")


def database(authors, articles_each):
    engine = create_engine("sqlite://")
    Base.metadata.create_all(engine)
    with Session(engine) as s, s.begin():
        for i in range(authors):
            author = Author(name=f"author {i}")
            author.articles = [Article(title=f"article {i}.{j}") for j in range(articles_each)]
            s.add(author)
    return engine


def measure(engine, work):
    """Run work(session); return (statements sent, rows those statements return)."""
    sent = []

    def record(conn, cursor, statement, params, context, executemany):
        sent.append((statement, params))

    event.listen(engine, "before_cursor_execute", record)
    with Session(engine) as s:
        work(s)
    event.remove(engine, "before_cursor_execute", record)
    with engine.connect() as conn:
        raw = conn.connection.cursor()
        rows = sum(len(raw.execute(sql, params).fetchall()) for sql, params in sent)
    return len(sent), rows


def article_authors(options=()):
    def work(s):
        for a in s.scalars(select(Article).options(*options)):
            a.author.name
    return work


def author_articles(options=(), unique=False):
    def work(s):
        result = s.scalars(select(Author).options(*options))
        for author in (result.unique() if unique else result):
            len(author.articles)
    return work


if __name__ == "__main__":
    print("many-to-one, article.author: 100 articles")
    one_each = database(authors=100, articles_each=1)
    ten = database(authors=10, articles_each=10)
    print("  lazy, 100 distinct authors  ", measure(one_each, article_authors()))
    print("  lazy, 10 distinct authors   ", measure(ten, article_authors()))
    print("  joinedload                  ", measure(one_each, article_authors([joinedload(Article.author)])))
    print("  selectinload                ", measure(one_each, article_authors([selectinload(Article.author)])))

    print("one-to-many, author.articles: 100 authors x 50 articles")
    fifty = database(authors=100, articles_each=50)
    print("  lazy                        ", measure(fifty, author_articles()))
    print("  joinedload (.unique())      ", measure(fifty, author_articles([joinedload(Author.articles)], unique=True)))
    print("  selectinload                ", measure(fifty, author_articles([selectinload(Author.articles)])))
    print("(statements sent, rows returned)")

Its output:

many-to-one, article.author: 100 articles
  lazy, 100 distinct authors   (101, 200)
  lazy, 10 distinct authors    (11, 110)
  joinedload                   (1, 100)
  selectinload                 (2, 200)
one-to-many, author.articles: 100 authors x 50 articles
  lazy                         (101, 5100)
  joinedload (.unique())       (1, 5000)
  selectinload                 (2, 5100)
(statements sent, rows returned)

14Try it by hand

Fifteen minutes at a Python prompt: build two tables, watch SQLAlchemy write every statement, cause N+1 on purpose, fix it, and meet the errors from this page in person. Every step was run on 22 November 2026 with SQLAlchemy 2.0.51, Python 3.14 and, for the bonus, Flask 3.1.3 with Flask-SQLAlchemy 3.1.1; the output below is copied from that run.

You need Python 3.9 or newer and a terminal. The database is a SQLite file, so there is nothing else to install or start.

1

2

Save the models as models.py

The two classes from section 5, an engine with echo=True so that every statement is printed, and a tiny counter, sent(), that tells you how many statements reached the database since you last asked.

from sqlalchemy import ForeignKey, create_engine, event, select, update
from sqlalchemy.orm import (DeclarativeBase, Mapped, Session, joinedload, mapped_column,
                            raiseload, relationship, selectinload)

engine = create_engine("sqlite:///blog.db", echo=True)   # echo: print every statement


class Base(DeclarativeBase):
    pass


class Author(Base):
    __tablename__ = "authors"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    articles: Mapped[list["Article"]] = relationship(back_populates="author")


class Article(Base):
    __tablename__ = "articles"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    author_id: Mapped[int] = mapped_column(ForeignKey("authors.id"))
    author: Mapped[Author] = relationship(back_populates="articles")


statements = []


@event.listens_for(engine, "before_cursor_execute")
def remember(conn, cursor, statement, params, context, executemany):
    statements.append(statement)


def sent():
    """How many statements reached the database since the last call."""
    count = len(statements)
    statements.clear()
    return count
3

Start Python with the models loaded, and create the tables

python -i models.py

The -i runs the file and leaves you at the >>> prompt with everything in it defined. Now:

>>> Base.metadata.create_all(engine)
CREATE TABLE authors (
	id INTEGER NOT NULL,
	name VARCHAR NOT NULL,
	PRIMARY KEY (id)
)
CREATE TABLE articles (
	id INTEGER NOT NULL,
	title VARCHAR NOT NULL,
	author_id INTEGER NOT NULL,
	PRIMARY KEY (id),
	FOREIGN KEY(author_id) REFERENCES authors (id)

Each echo line really starts with a timestamp and INFO sqlalchemy.engine.Engine; they are cut here. Look at name VARCHAR NOT NULL: you never wrote NOT NULL. Mapped[str] did (section 5). There is no articles or author column either: a relationship is not a column.

4

Add three authors and six articles

>>> s = Session(engine)
>>> ann, bob, cat = Author(name="Ann"), Author(name="Bob"), Author(name="Cat")
>>> s.add_all([Article(title=f"Post {i}", author=a) for i, a in enumerate([ann, bob, cat, ann, bob, cat], 1)])
>>> s.commit()
BEGIN (implicit)
INSERT INTO authors (name) VALUES (?) RETURNING id   # three times
INSERT INTO articles (title, author_id) VALUES (?, ?) RETURNING id   # six times
COMMIT

You added only articles, and never set an author_id. The session found the authors through the relationship, inserted them first, and used their new ids for the articles: parents before children, the unit of work from section 6. Nothing was sent until commit().

5

Change a title, and watch the UPDATE write itself

>>> a = s.get(Article, 1)
BEGIN (implicit)
SELECT articles.id AS articles_id, articles.title AS articles_title, articles.author_id AS articles_author_id
FROM articles
WHERE articles.id = ?
>>> a.title = "Hello, world"
>>> s.commit()
UPDATE articles SET title=? WHERE articles.id = ?
COMMIT

The assignment printed nothing: it only changed an object. The UPDATE appeared at commit(), written from what you changed, with the values as bound parameters (the ?), never pasted into the SQL.

6

One row, one object

>>> sent()                      # starts the count from zero; ignore this number
17
>>> a = s.get(Article, 2)
SELECT articles.id AS articles_id, ... WHERE articles.id = ?
>>> b = s.get(Article, 2)
>>> a is b
True
>>> sent()
1

Two calls, one SELECT, and the same object: the identity map (section 7). The second get did not go to the database at all.

7

The four lines from the video — predict first

Six articles by three authors. Before you press Enter twice, write down how many statements you expect. Then:

>>> s.close(); s = Session(engine); sent()   # a fresh session, and the count back to zero
>>> for a in s.scalars(select(Article)):
...     print(a.title, a.author.name)
...
SELECT articles.id, articles.title, articles.author_id FROM articles
SELECT authors.id AS authors_id, authors.name AS authors_name FROM authors WHERE authors.id = ?
Hello, world Ann
Post 4 Ann
SELECT authors.id AS authors_id, authors.name AS authors_name FROM authors WHERE authors.id = ?
Post 2 Bob
Post 5 Bob
SELECT authors.id AS authors_id, authors.name AS authors_name FROM authors WHERE authors.id = ?
Post 3 Cat
Post 6 Cat
>>> sent()
4

Watch where the SELECTs fall: between the printed lines. Each one fires the moment a.author is first touched. And it is 4, not 7: one for the list, then one per distinct author. Ann's second article found Ann already in the session. That is section 8's eleven, in miniature: with six authors you would have seen 7.

8

Fix it, twice

>>> s.close(); s = Session(engine); sent()
>>> for a in s.scalars(select(Article).options(joinedload(Article.author))):
...     print(a.title, a.author.name)
...
SELECT articles.id, articles.title, articles.author_id, authors_1.id AS id_1, authors_1.name
FROM articles LEFT OUTER JOIN authors AS authors_1 ON authors_1.id = articles.author_id
(the six lines print, with no SQL between them)
>>> sent()
1

Now run the same with selectinload(Article.author) in place of joinedload, in a fresh session again. You get two statements, the second one ... WHERE authors.id IN (?, ?, ?), and sent() says 2. The loop never changed; only the question did.

9

Make an accidental lazy load loud

>>> s.close(); s = Session(engine)
>>> a = s.scalars(select(Article).options(raiseload(Article.author))).first()
>>> a.author
sqlalchemy.exc.InvalidRequestError: 'Article.author' is not available due to lazy='raise'

In a test suite, this turns a silent extra query into a failing test (section 10).

10

Meet the ghost

>>> s.close(); s = Session(engine)
>>> a = s.get(Article, 1)
>>> s.commit()
>>> s.close()
>>> a.title
sqlalchemy.orm.exc.DetachedInstanceError: Instance <Article at 0x...> is not bound to a Session;
attribute refresh operation cannot proceed

The commit expired a's attributes, so reading a.title needs the database again, and the session that could ask is closed. The object in your hand is a ghost. Two ways out: read what you need before the session closes, or open it as Session(engine, expire_on_commit=False), and then a.title still works after close().

11

One statement for many rows

>>> s = Session(engine)
>>> r = s.execute(update(Article).where(Article.author_id == 1).values(title="Draft"))
BEGIN (implicit)
UPDATE articles SET title=? WHERE articles.author_id = ?
>>> r.rowcount
2
>>> s.commit()
COMMIT

Both of Ann's articles changed, no object was loaded, and one UPDATE did it: Core inside the same session (section 4). Type exit() to leave Python. To start the whole exercise over, delete blog.db.

Bonus — the same in Flask (ten minutes)

In a web app, the session belongs to one request. Flask-SQLAlchemy sets that up, and it can also count each request's statements so you can watch N+1 in the browser.

12

Install Flask and Flask-SQLAlchemy

pip install flask flask-sqlalchemy
13

Save blog_app.py

from flask import Flask, request
from flask_sqlalchemy import SQLAlchemy
from flask_sqlalchemy.record_queries import get_recorded_queries
from sqlalchemy import ForeignKey, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, selectinload


class Base(DeclarativeBase):
    pass


db = SQLAlchemy(model_class=Base)
app = Flask(__name__)
app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///blog_app.db"   # created in instance/
app.config["SQLALCHEMY_RECORD_QUERIES"] = True                    # count each request's SQL
db.init_app(app)


class Author(db.Model):
    __tablename__ = "authors"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    articles: Mapped[list["Article"]] = relationship(back_populates="author")


class Article(db.Model):
    __tablename__ = "articles"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    author_id: Mapped[int] = mapped_column(ForeignKey("authors.id"))
    author: Mapped[Author] = relationship(back_populates="articles")


with app.app_context():
    db.create_all()
    if db.session.scalar(select(Article).limit(1)) is None:     # add the data only once
        ann, bob, cat = Author(name="Ann"), Author(name="Bob"), Author(name="Cat")
        db.session.add_all([Article(title=f"Post {i}", author=a)
                            for i, a in enumerate([ann, bob, cat, ann, bob, cat], 1)])
        db.session.commit()


@app.route("/")
def index():
    query = select(Article)
    if request.args.get("eager"):
        query = query.options(selectinload(Article.author))
    lines = [f"{a.title} by {a.author.name}" for a in db.session.scalars(query)]
    lines.append(f"<b>Statements this request: {len(get_recorded_queries())}</b>")
    return "<br>".join(lines)
14

Run it, and count in the browser

flask --app blog_app run --debug

Open http://127.0.0.1:5000/. Six lines, and at the bottom Statements this request: 4: the same N+1 as step 7, now inside a request. Open http://127.0.0.1:5000/?eager=1 and it says 2. Reload either page as often as you like: the count stays the same, because every request gets a fresh session that Flask-SQLAlchemy closes when the response is sent. The database file is in a new instance/ folder, where Flask-SQLAlchemy puts a relative SQLite path. Stop the server with Ctrl+C.

What you just saw, by hand. The class wrote the schema (3). The session ordered the INSERTs (4) and wrote the UPDATE (5). One row was one object (6). A dot ran a query, and the count was 1 + distinct authors (7). One option fixed it without touching the loop (8). A lazy load can be made to fail loudly (9). A closed session leaves ghosts (10). And when you need it, one statement still does the work of many (11).
