1What async is not

Video: slide 3

"Async makes your code faster" is the sentence to drop first. It does not. It makes waiting cheap.

  • Nothing runs in parallel. asyncio is one thread on one core, and the GIL still holds.
  • No computation gets faster. Four CPU-bound tasks under asyncio.gather came out at 0.97× of serial (section 9).
  • What changes is the cost of waiting. Ten thousand simultaneous waits become cheap. That is the entire feature: a narrower claim than "faster", but where it applies, it applies enormously.

If someone rewrote a CPU-heavy script in asyncio and it got faster, something else changed at the same time. Ask what.

2Concurrency and parallelism

Video: slide 4

ConcurrencyParallelism
Dealing with many things at onceDoing many things at once
A structure: many tasks in flight, progress interleaved. One cook managing four pans.An execution fact: two things in the same instant, on two cores. Four cooks at four stations.
Threads and asyncio both give you this.In CPython, only processes give you this.

The distinction is Rob Pike's, from a 2012 talk about Go: concurrency is about structure, parallelism is about execution. asyncio is a concurrency tool, exclusively. It never adds a core, so every question about it comes down to one: is this program waiting, or working?

3The event loop

Video: slide 5

  1. Take the next ready task and run it: ordinary, synchronous Python.
  2. Run it until it hits an await: the task saying "I am waiting on something; here is control back".
  3. Park it, and register the wait. The loop hands the socket or timer to the operating system and forgets the task.
  4. Go back to step 1. When the OS reports the wait is over, the task is ready again.

One thread, one task at a time, from one await to the next. Nothing interrupts a task in the middle; the OS is not scheduling any of this, the tasks cooperate. That is why you need no locks between two awaits, and why one task that refuses to yield stops everybody (section 7).

4Coroutines and tasks

Video: slide 6

async def fetch():
    await asyncio.sleep(1)
    return 42

c = fetch()      # nothing has happened
print(c)         # <coroutine object fetch>

result = await fetch()      # now it runs
  • A coroutine is a paused function: its local variables and its position in the code, waiting to be resumed.
  • Calling it does nothing. Forget the await and Python warns: RuntimeWarning: coroutine 'fetch' was never awaited.
  • A task is a scheduled coroutine. asyncio.create_task() hands it to the loop, and that is what makes things run concurrently.

The sequential-await trap. await a(); await b(); await c() is not concurrent: three one-second waits take three seconds (try it in step 2 below). Concurrency starts when several are in flight together: asyncio.gather(a(), b(), c()) takes one second, and so does a TaskGroup.

5The syntax worth knowing

Not in the video

# fan out, wait for all
results = await asyncio.gather(a(), b(), c())

# structured concurrency - 3.11+, and the better default
async with asyncio.TaskGroup() as tg:
    tg.create_task(a())
    tg.create_task(b())

# a deadline
async with asyncio.timeout(5):
    await slow_thing()

# at most ten at a time
limit = asyncio.Semaphore(10)
async with limit:
    await fetch(url)
  • Prefer TaskGroup to gather. If one task fails, the group cancels the rest and raises an ExceptionGroup. Plain gather can leave the siblings running, unwatched.
  • Always bound your concurrency. gather over 10,000 URLs opens 10,000 sockets; a Semaphore is the difference between fast and banned.
  • Cancellation is an exception, CancelledError, raised inside the task. Let it propagate: a bare except that swallows it turns a clean shutdown into a hang.

TaskGroup and asyncio.timeout arrived in Python 3.11 and made most older patterns obsolete. A tutorial built on ensure_future predates them.

6Five thousand waits, and why a coroutine is cheap

Video: slide 7

The same two-second wait, N of them at once, threads against coroutines. Means of eight runs of async_bench.py (section 15), Python 3.14.3, 8 cores:

N at onceThreads: time · memoryCoroutines: time · memory
1002.02 s · 2.5 MB2.01 s · 0.1 MB
1,0002.13 s · 24.8 MB2.03 s · 0.2 MB
5,0002.68 s · 124.2 MB2.10 s · 0.8 MB

About 150× less memory. Both wait perfectly well; the threads even got slower, because five thousand OS threads cost real scheduling effort. The argument for async is a memory argument, about the ceiling, not a speed one.

A threadA coroutine
Its own call stack, reserved up frontA Python object holding locals and a position
Kernel bookkeeping: the OS schedules itThe kernel does not know it exists
A switch is a trip into the kernelA switch is a function return, no system call
About 25 KB each here (124.2 MB / 5,000)About 170 bytes each here (0.8 MB / 5,000)

A few thousand threads is a lot for one machine; a few hundred thousand coroutines is unremarkable. For a service that holds many idle connections (websockets, long polling, server-sent events, streaming) that ceiling is the whole design constraint, and it is why FastAPI can do things Flask cannot.

7One blocking call

Video: slide 8

One event loop, a few trivial tasks that each wait 10 ms, and one slow task that takes a second. How long did the 10 ms tasks take? Means of eight runs:

The slow task usesThe 10 ms task tookWhy
time.sleep(1)1,018.6 msIt blocks: the loop cannot run anything else
await asyncio.sleep(1)14.5 msIt yields: everyone else proceeds
await asyncio.to_thread(time.sleep, 1)30.4 msIt runs on a thread: the loop stays free

A hundred times its own duration, because something else refused to yield and nothing can force it. In a web service that is every other request on the worker. A synchronous framework would have blocked one worker out of several, and the OS would pre-empt it anyway; on an event loop, scheduling is cooperative, and a task that does not cooperate takes everyone down with it.

8The escape hatches, and debug mode

Video: slide 9

# a blocking library, in an async handler
rows = await asyncio.to_thread(legacy_query, sql)

# CPU-bound work - a process, not a thread
loop = asyncio.get_running_loop()
with ProcessPoolExecutor() as pool:
    out = await loop.run_in_executor(pool, crunch, data)
  • to_thread for blocking I/O: a legacy driver, a file read, an SDK with no async version. The loop stays free.
  • A process pool for CPU work: a thread would not help, because the GIL has not gone anywhere.
  • Or a synchronous framework: if most of your work blocks, async is a costume. Flask with more Gunicorn workers is simpler and more honest.

Debug mode finds the blocking calls you did not know about. Set PYTHONASYNCIODEBUG=1, or call asyncio.run(main(), debug=True), and the loop logs every callback that took longer than 100 ms: Executing <Task … coro=<handler() …> took 0.302 seconds (step 4 below). It is the async counterpart of echo=True in an ORM.

9It still cannot compute

Not in the video (its numbers are on slide 10)

Four CPU-bound tasks (5,000,000 squares each), gathered on the event loop: 3.41 s serial against 3.56 s with asyncio.gather. The ratio is 0.97×, and across the eight runs it moved between 0.78× and 1.12×: it scatters around one. Tasks switch only at await, and a tight arithmetic loop has none.

ToolWaitingComputing
threads3.99×1.07×
asyncioscales to thousands0.97×
processes2.85×2.36×

Measured on the same laptop, four workers on four tasks; the threads and processes rows come from the GIL talk (its notes). Three tools, one question: is the program waiting, or working?

10Choosing between the three

Video: slide 10

UseWhenFor example
asyncioMany waits: hundreds or thousands at onceWeb servers holding connections, scrapers, chatty API clients, websockets
threadingA few waits, or a blocking library you cannot replaceA handful of parallel downloads, an SDK with no async support
multiprocessingReal computation in PythonData crunching, parsing, hashing, image work

Async and threads solve the same problem; they differ in ceiling, not in kind. And the fourth option is usually right: do nothing. Most services are waiting on one database that answers in five milliseconds, and no concurrency machinery improves that.

11Async all the way down

Not in the video

Every library on the hot path needs an async version, because one synchronous library in the chain and the whole benefit disappears:

Instead ofUse
psycopg2asyncpg, PostgreSQL's async-native driver
SQLAlchemy's SessionAsyncSession, SQLAlchemy 2.0's async ORM session
requestshttpx, with an async client
redis-py's clientredis.asyncio, which ships inside redis-py
open()aiofiles: file I/O is otherwise always blocking
engine = create_async_engine(DATABASE_URL)
async with AsyncSession(engine) as session:
    result = await session.scalars(select(Word))

An async framework calling psycopg2 is a synchronous application wearing async syntax, and it is worse than the synchronous version: every query blocks the loop, with no OS pre-emption to soften it. That is the most common way async projects end up slower than what they replaced, so check the hot path first. And the failure modes multiply: an ORM's N+1 problem, a hundred and one queries, on a blocked loop stalls every other request on the worker too.

12ASGI

Video: slide 11

# WSGI: one call, one response
def app(environ, start_response):
    ...
    return [b"body"]

# ASGI: a coroutine, and two channels
async def app(scope, receive, send):
    ...
    await send({...})

WSGI takes a dict and returns bytes: there is nowhere in that shape for a connection that stays open, which is why WSGI cannot do websockets. ASGI can receive many messages and send many, so websockets and streaming fit. A plain HTTP response is two messages, http.response.start (status and headers) and http.response.body; step 7 below calls an ASGI app by hand and prints them. ASGI was inspired by WSGI rather than derived from it: a separate design for connections that persist, not a version two.

Uvicorn is to ASGI what Gunicorn is to WSGI, and you still run several Uvicorn workers: async gives concurrency inside one core, worker processes give parallelism across cores. Two problems, two tools, and a real deployment needs both.

13When not to use it

Not in the video

  • Your work is CPU-bound. Threads gave 1.07×, asyncio 0.97×: neither helps. Use processes.
  • Your libraries are synchronous. One blocking driver undoes the whole thing, and makes it worse than sync would have been (section 11).
  • Your concurrency is in the dozens. Threads are simpler, and the ceiling matters only in the thousands.
  • The team has not written it before. Async is contagious: one await makes its caller async, and that caller's caller, all the way up to the entry point. There is no small async pilot inside a synchronous codebase; it is a codebase-wide decision.

Flask with more Gunicorn workers handles a great deal of traffic and is understood by everyone you will ever hire. Reach for async for a specific reason, many concurrent connections, not because it is the newer keyword.

14The interview answer

Video: slide 12

An async handler calls a synchronous database driver. What happens, and why is it worse than the same call in a synchronous framework?

  1. What happens: the blocking call holds the single event-loop thread, so every coroutine on that worker stops, not just the current request.
  2. Why it is worse than sync: a synchronous framework blocks one worker of several, and the OS pre-empts it anyway; on a loop, nothing pre-empts you.
  3. The number: a 10 ms task behind one blocking second took 1,019 ms on average, a hundred times its own duration.
  4. The fix: an async driver, or asyncio.to_thread, found with debug mode.

Async does not make code faster. It makes waiting cheap — and it charges you the whole codebase for it.

15Run it yourself

Every number in the video and on this page comes from async_bench.py: pip install psutil (it measures the process's memory), then python async_bench.py. The figures are means of eight runs, each in a fresh process, Python 3.14.3 on 8 cores, 1 October 2026; your machine will give different numbers, and the same shape.

"""Measure what async actually buys you, and what it costs.

Three experiments:
  1. Concurrency at scale — N simultaneous waits, threads vs coroutines.
  2. Blocking the event loop — what one sync call does to everything else.
  3. CPU-bound under asyncio — proof that async is not a speed-up.

    python async_bench.py
"""

import asyncio
import gc
import os
import sys
import threading
import time

import psutil

PROC = psutil.Process(os.getpid())
WAIT = 2.0


def rss_mb() -> float:
    gc.collect()
    return PROC.memory_info().rss / 1024 / 1024


# ------------------------------------------------ 1. concurrency at scale --
def threads_wait(n: int):
    ts = [threading.Thread(target=time.sleep, args=(WAIT,)) for _ in range(n)]
    base = rss_mb()
    t0 = time.perf_counter()
    for t in ts:
        t.start()
    peak = rss_mb()
    for t in ts:
        t.join()
    return time.perf_counter() - t0, peak - base


async def _coros_wait(n: int):
    base = rss_mb()
    t0 = time.perf_counter()
    tasks = [asyncio.create_task(asyncio.sleep(WAIT)) for _ in range(n)]
    await asyncio.sleep(0)          # let them all start
    peak = rss_mb()
    await asyncio.gather(*tasks)
    return time.perf_counter() - t0, peak - base


def coros_wait(n: int):
    return asyncio.run(_coros_wait(n))


# ------------------------------------------------ 2. blocking the loop -----
async def _loop_blocking(mode: str):
    """One slow task, then measure how long a trivial task waits behind it."""
    latencies = []

    async def slow():
        if mode == "sync":
            time.sleep(1.0)                      # blocks the whole loop
        elif mode == "async":
            await asyncio.sleep(1.0)             # yields
        else:
            await asyncio.to_thread(time.sleep, 1.0)   # offloaded

    # The clock has to start BEFORE anything is scheduled. Timing from inside
    # quick() would start counting only once it first runs -- which is after
    # the blocking call has already finished, so the delay would be invisible.
    async def quick(started: float):
        await asyncio.sleep(0.01)                # should take ~10ms
        latencies.append((time.perf_counter() - started) * 1000)

    started = time.perf_counter()
    await asyncio.gather(slow(), *[quick(started) for _ in range(5)])
    return max(latencies)


def loop_blocking(mode: str):
    return asyncio.run(_loop_blocking(mode))


# ------------------------------------------------ 3. CPU-bound under async -
def cpu(n=5_000_000):
    total = 0
    for i in range(n):
        total += i * i
    return total


async def _cpu_async():
    async def one():
        return cpu()
    t0 = time.perf_counter()
    await asyncio.gather(*[one() for _ in range(4)])
    return time.perf_counter() - t0


def cpu_serial():
    t0 = time.perf_counter()
    for _ in range(4):
        cpu()
    return time.perf_counter() - t0


if __name__ == "__main__":
    print(f"Python {sys.version.split()[0]}   cores: {os.cpu_count()}\n")

    print("=" * 70)
    print(f"1. {int(WAIT)}-second wait, N at once")
    print("=" * 70)
    print(f"{'N':>6}  {'threads: time / memory':>28}  {'coroutines: time / memory':>28}")
    for n in (100, 1000, 5000):
        try:
            tt, tm = threads_wait(n)
            tcol = f"{tt:6.2f}s / {tm:7.1f} MB"
        except (RuntimeError, MemoryError) as exc:
            tcol = f"FAILED: {type(exc).__name__}"
        ct, cm = coros_wait(n)
        print(f"{n:>6}  {tcol:>28}  {ct:6.2f}s / {cm:7.1f} MB")

    print("\n" + "=" * 70)
    print("2. One slow call, and how long a 10ms task waits behind it")
    print("=" * 70)
    for mode, label in [("sync", "time.sleep(1)        blocking"),
                        ("async", "await asyncio.sleep(1)"),
                        ("thread", "await to_thread(sleep, 1)")]:
        print(f"  {label:32} worst 10ms task took {loop_blocking(mode):8.1f} ms")

    print("\n" + "=" * 70)
    print("3. CPU-bound work under asyncio (4 x 5,000,000 squares)")
    print("=" * 70)
    s = cpu_serial()
    a = asyncio.run(_cpu_async())
    print(f"  serial          {s:6.2f}s")
    print(f"  asyncio.gather  {a:6.2f}s   ->  {s/a:.2f}x")

16Try it by hand

Seven small scripts, ten minutes. Each one shows one idea from this page; save it, run it, and compare with the output below. Every script was run on 23 November 2026 with Python 3.14.3, and the output is copied from that run (your times will differ a little). You need Python 3.11 or newer, and nothing to install.

1

A coroutine is an object that has not started

Calling an async function gives you a coroutine object; only await runs it. The last line calls fetch() and drops the result: Python warns that it was never awaited. Save it as step1_coroutine.py and run python step1_coroutine.py.

import asyncio


async def fetch():
    await asyncio.sleep(1)
    return 42


async def main():
    c = fetch()
    print(c)                 # a coroutine object: nothing has run yet
    print(await c)           # now it runs, and returns 42
    fetch()                  # called, never awaited


asyncio.run(main())

Three awaits in a row, then gather

The same three one-second waits, first awaited one after another, then gathered. Then five thousand at once. Save it as step2_gather.py and run python step2_gather.py.

import asyncio
import time


async def wait(n):
    await asyncio.sleep(1)
    return n


async def main():
    t0 = time.perf_counter()
    print(await wait(1), await wait(2), await wait(3))
    print(f"three awaits in a row: {time.perf_counter() - t0:.2f} s")

    t0 = time.perf_counter()
    print(await asyncio.gather(wait(1), wait(2), wait(3)))
    print(f"gather of three: {time.perf_counter() - t0:.2f} s")

    t0 = time.perf_counter()
    results = await asyncio.gather(*[wait(i) for i in range(5000)])
    print(f"gather of {len(results)}: {time.perf_counter() - t0:.2f} s")


asyncio.run(main())

One blocking call stops everybody

Five 10 ms tasks share a loop with one slow call. The slow call is first time.sleep, then asyncio.sleep, then time.sleep on a thread. Save it as step3_freeze.py and run python step3_freeze.py.

import asyncio
import time


async def quick(started):
    await asyncio.sleep(0.01)                         # a 10 ms task
    return (time.perf_counter() - started) * 1000


async def run(slow):
    started = time.perf_counter()
    results = await asyncio.gather(slow(), *[quick(started) for _ in range(5)])
    return max(results[1:])


async def blocking():
    time.sleep(1)                                     # blocks the whole loop


async def polite():
    await asyncio.sleep(1)                            # yields


async def offloaded():
    await asyncio.to_thread(time.sleep, 1)            # runs on a thread


for slow in (blocking, polite, offloaded):
    print(f"{slow.__name__:10} the 10 ms task took {asyncio.run(run(slow)):7.1f} ms")
blocking   the 10 ms task took  1010.9 ms
polite     the 10 ms task took    10.9 ms
offloaded  the 10 ms task took    32.1 ms

A TaskGroup cleans up after a failure

Two slow tasks and one that fails. The group cancels the other two and raises an ExceptionGroup, which except* unpacks. Save it as step5_taskgroup.py and run python step5_taskgroup.py.

import asyncio


async def slow(name):
    try:
        await asyncio.sleep(5)
    except asyncio.CancelledError:
        print(name, "was cancelled")
        raise                      # let cancellation through


async def boom():
    await asyncio.sleep(0.1)
    raise ValueError("boom")


async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(slow("a"))
            tg.create_task(slow("b"))
            tg.create_task(boom())
    except* ValueError as group:
        print("the group raised:", group.exceptions)


asyncio.run(main())
b was cancelled
a was cancelled
the group raised: (ValueError('boom'),)

A semaphore bounds concurrency

Nine one-second tasks, at most three at a time. Save it as step6_semaphore.py and run python step6_semaphore.py.

import asyncio
import time

limit = asyncio.Semaphore(3)       # at most three at a time


async def polite(n):
    async with limit:
        await asyncio.sleep(1)
        return n


async def main():
    t0 = time.perf_counter()
    await asyncio.gather(*[polite(i) for i in range(9)])
    print(f"9 one-second tasks, 3 at a time: {time.perf_counter() - t0:.2f} s")


asyncio.run(main())
9 one-second tasks, 3 at a time: 3.00 s

ASGI by hand

An ASGI application is a coroutine with two channels. Calling it directly, with a hand-made receive and send, shows the two messages a plain HTTP response is made of. Save it as step7_asgi.py and run python step7_asgi.py.

import asyncio


async def app(scope, receive, send):                  # an ASGI application
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain")]})
    await send({"type": "http.response.body", "body": b"Hello from ASGI"})


async def receive():
    return {"type": "http.request", "body": b""}


async def send(message):
    print(message)


scope = {"type": "http", "method": "GET", "path": "/"}
asyncio.run(app(scope, receive, send))
{'type': 'http.response.start', 'status': 200, 'headers': [(b'content-type', b'text/plain')]}
{'type': 'http.response.body', 'body': b'Hello from ASGI'}

What you just saw, by hand. A coroutine is an object that has not started (1). Concurrency needs several in flight at once (2). One blocking call stops everybody, and to_thread sets them free (3). Debug mode names the culprit (4). A TaskGroup cleans up after a failure (5). A semaphore keeps you polite (6). And ASGI is just a coroutine that sends messages (7).
