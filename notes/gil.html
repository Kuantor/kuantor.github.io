1The open question

Video: slide 2

In the Flask talk, the development server ran the app as one process, with a thread for each request. But the WSGI talk deployed a Python web application as several complete, separate processes behind one server. Nobody asked why. Threads are lighter, share memory and start faster, and almost every other language would have used them there. Python does not, and the reason is one design decision inside the interpreter: the Global Interpreter Lock.

2Python and CPython

Video: one sentence on slide 3

Python is a language specification: what for, def and yield mean. It is essentially a document, and it says nothing at all about a GIL. CPython is software, written in C, that reads your source, compiles it to bytecode and runs it; it was written by Guido van Rossum, and it is the reference implementation. The GIL lives in CPython. If you downloaded Python from python.org, you are running CPython, which is why "Python has a GIL" is a useful shorthand and a technically wrong sentence. Saying "CPython's GIL" is a small precision interviewers notice.

EngineGIL?
CPythonyesThe reference implementation, in C. What python.org gives you.
PyPyyesA JIT compiler, often several times faster on long-running pure-Python code. Same lock.
JythonnoRuns on the JVM and uses Java's threads: real parallelism, but stuck on Python 2.7.
IronPythonnoRuns on .NET. Genuine threading, and an older language version.

The GIL-free engines are years behind on the language and most of the library ecosystem. That trade is why, for thirty years, almost nobody made it.

3What the GIL is

Video: slide 3

A mutex, one per interpreter process, which a thread must hold to execute Python bytecode. So only one thread executes Python bytecode at a time, however many cores the machine has. Three things it is not:

  • Not a lock on your data. It does not make your code thread-safe: two threads can still interleave between a read and a write and lose an update. Step 6 below loses most of 8,000 deposits that way. You still need your own locks around shared data.
  • Not held continuously. The interpreter drops it every few milliseconds, and on any blocking I/O. Threads really do interleave; they just never run Python at the same instant.
  • Per process, not per machine. Two Python programs have two GILs and use two cores happily.

The kitchen. Ten chefs, one knife. All ten can work: fetching, washing, waiting for the oven. Only one can be chopping, and they hand the knife over to swap. More chefs do not chop the onions faster; they get everything else done while one chops. That last sentence is the whole answer to "when does threading still help?"

4Why it exists

Video: slide 4

  1. Reference counting. CPython frees an object when the count of references to it reaches zero, and that count changes on almost every operation (step 2 below shows it). Two threads updating it at once is a race: crashes, leaks, objects freed while still in use. One global lock removes the whole class of bug.
  2. Simplicity and single-threaded speed. The alternative, a lock on every object, is far more complex and makes ordinary single-threaded code slower, and most Python code is single-threaded.
  3. C extensions. Their authors could write C without thinking about concurrent access. NumPy, SciPy and pandas exist partly because that was easy.

Every serious attempt to remove the GIL before about 2023 succeeded at removing it and failed on the same point: the interpreter got slower at single-threaded code. That is why it survived thirty years.

5CPU-bound: threads do not help

Video: slides 5 and 6

Four tasks, each summing six million squares in a pure Python loop, run serially, on four threads, and on four processes. Means of eight runs of gil_bench.py (section 16), Python 3.14.3, 8 cores, GIL enabled:

Serial4 threads4 processes
2.83 s2.65 s · 1.07×1.20 s · 2.36×

Across the eight runs the thread figure moved between 0.98× and 1.15×: it scatters around 1.0, sometimes a shade slower, sometimes a shade faster, never meaningfully faster. The threads spend their time taking the lock, running some bytecode and handing it back. Eight cores, one used. The processes reach 2.36×, not 4×, because starting an interpreter and moving data into it is not free: parallelism has a floor price.

6I/O-bound: threads help enormously

Video: slide 7

Serial4 threads4 processes
3.00 s0.75 s · 3.99×1.05 s · 2.85×

Four tasks that each wait three quarters of a second finished in three quarters of a second: a thread that is waiting runs no bytecode, so it hands the lock back. Unlike the CPU figure, this one barely moves: 3.95× to 4.0× across the runs. The hundred and one queries of the ORMs talk's N+1 problem are this kind of work: each one waits on the database, with the lock handed back. And processes do worse than threads here, because they solve a problem you do not have and charge the startup cost anyway. "Use multiprocessing" is advice for one case, not general advice.

8Why the difference

Video: slide 8

# CPU-bound - the lock is held the whole time
for i in range(6_000_000):
    total += i * i        # bytecode, bytecode, bytecode...

# I/O-bound - the lock is handed back at the call
data = sock.recv(4096)   # GIL released here
                         # ... other threads run ...
                         # GIL re-acquired when data arrives

Waiting is not executing. Before any blocking system call (a socket read, a disk access, a sleep) CPython releases the lock, and takes it back when the call returns; it also drops it every few milliseconds so no thread starves. You never write any of this.

Threads in Python give you concurrency while waiting, not parallelism while computing. So the question is never "threads or processes?" but "is this work waiting, or computing?"

Most web backends are almost entirely I/O-bound: they spend their lives waiting for the database. That is why Python is a perfectly good language for web work, GIL and all.

10multiprocessing, at a price

Not in the video

from concurrent.futures import ProcessPoolExecutor

if __name__ == "__main__":     # required on Windows and macOS
    with ProcessPoolExecutor(4) as pool:
        results = list(pool.map(cpu_task, data))
  • Startup is not free: a new interpreter per process. Measured above: 2.36× rather than 4×.
  • Memory is not shared: arguments and results are pickled and copied, and large data can cost more to move than to process.
  • Not everything pickles: lambdas, open sockets, database connections. Pass identifiers, and let each worker open its own.

The if __name__ == "__main__" guard is not style. On Windows and macOS, child processes re-import your module to find the function they should run. Without the guard, they re-run your top-level code, which tries to start processes of its own.

And the simplest version of all: two python commands in two terminals are two processes, two GILs, two cores. The GIL only ever restricted threads inside one process.

11The third option: asyncio

Not in the video; it is the next talk

threadingasyncio
OS threads, pre-emptive: the OS can switch at any moment, so shared state needs locks.One thread, cooperative: it switches only at an await, which you can see in the source.

Neither escapes the GIL: both are single-core. asyncio is not a way around the lock; it is a way to hold it more efficiently while waiting, and it scales further, because a coroutine costs a few hundred bytes where a thread brings its own stack. A rule of thumb: a few dozen concurrent waits, threads are fine; thousands, asyncio; computing, processes. And because nobody pre-empts a coroutine, one blocking call inside an async handler stalls everything (measured in the Async notes).

12The escape hatch you already use

Video: an "If asked" on slide 9

import numpy as np

result = big_matrix @ other_matrix
#  the GIL is released for the duration of this

C extensions may release the GIL, and the word is may: the author must wrap the part that touches no Python objects in Py_BEGIN_ALLOW_THREADS and Py_END_ALLOW_THREADS. An extension that never does holds the lock like Python code. The ones you use every day do: NumPy, pandas, Pillow, cryptography, lxml and the database drivers drop into C, release the lock, do the work and take it back. So a NumPy-heavy workload across threads genuinely runs in parallel, while the same arithmetic as a Python loop does not.

Vectorise before you parallelise. The first fix for a slow numeric loop is usually not multiprocessing, but expressing the loop as an array operation and letting C do it: often a hundred times faster before any parallelism at all.

13Free-threaded Python

Video: one sentence on slide 11

  • PEP 703 (accepted 2023): make the GIL optional, behind a build flag.
  • Python 3.13 (2024): the first experimental free-threaded build.
  • Python 3.14: officially supported (PEP 779), still not the default build.
>>> import sys
>>> sys._is_gil_enabled()      # 3.13+
True                           # on the machine these benchmarks ran on

What it does not mean yet: it is not the default (you install a separate build deliberately); it is not free (one big lock becomes many small ones, and single-threaded code pays); it is not universally compatible (every C extension needs updating, and the ecosystem is part-way through); and it is not a reason to write threaded CPU-bound code today. In an interview, answer with the GIL as it is, then mention free-threading as what is coming.

14Where you have already met this

Video: slide 10

flask --app app run              # one process, a thread per request
gunicorn myapp:app --workers 4   # four processes, four GILs

Gunicorn's default model is pre-fork: a master process starts N workers, each a complete Python interpreter with its own GIL. That is the only way a Python web application uses more than one core, and the old rule, workers = 2 × cores + 1, is a GIL workaround wearing a formula.

  • The Flask development server is the other half: one process, a thread per request, which is fine on a laptop because a request spends its time waiting. Its reloader even runs your file in two processes, so two interpreters and two GILs.
  • Four pools, not one. Workers share nothing, so each holds its own connection pool. Size a pool at 10, run 8 workers, and the database sees 80 connections.
  • Celery uses worker processes for background jobs, for the same reason.
  • Uvicorn combines both: async inside each worker for waiting, several workers for the cores.
  • "Just add threads", sound advice in Java or Go, quietly does nothing here.

15The interview answer

Video: slide 11

  1. What it is: a mutex in CPython; one thread executes Python bytecode at a time, whatever the core count.
  2. Why: reference counting would race without it, and one coarse lock was simpler and faster than locking every object.
  3. When threads still help: I/O-bound work, because the lock is released while waiting. Four threads on four waits: 3.99×.
  4. When you need processes: CPU-bound pure Python, where threads measured 1.07×. Each process has its own interpreter and its own GIL.

Then one sentence more than they asked for: vectorise before you parallelise, and free-threaded builds exist but are not the default yet.

16Run it yourself

Every number in the video comes from gil_bench.py, standard library only: python gil_bench.py. The talk's figures are means of eight runs on Python 3.14.3 with 8 cores.

"""Measure the GIL: CPU-bound vs I/O-bound, threads vs processes."""
import os
import sys
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

N = 4
WORK = 6_000_000


def cpu_task(_):
    """Pure Python arithmetic - holds the GIL the whole time."""
    total = 0
    for i in range(WORK):
        total += i * i
    return total


def io_task(_):
    """Sleeping releases the GIL."""
    time.sleep(0.75)
    return 1


def timed(fn):
    t = time.perf_counter()
    fn()
    return time.perf_counter() - t


def serial(task):
    return lambda: [task(i) for i in range(N)]


def threaded(task):
    def run():
        with ThreadPoolExecutor(max_workers=N) as ex:
            list(ex.map(task, range(N)))
    return run


def processes(task):
    def run():
        with ProcessPoolExecutor(max_workers=N) as ex:
            list(ex.map(task, range(N)))
    return run


if __name__ == "__main__":
    print(f"Python  {sys.version.split()[0]}   cores: {os.cpu_count()}")
    gil = getattr(sys, "_is_gil_enabled", None)
    print(f"GIL enabled: {gil() if gil else 'n/a (pre-3.13)'}")
    print(f"CPU task: sum of {WORK:,} squares, x{N}    I/O task: sleep 0.75s x{N}\n")

    print(f"{'':22} {'serial':>9} {'threads':>9} {'processes':>10}   verdict")
    print("-" * 72)

    cs = timed(serial(cpu_task))
    ct = timed(threaded(cpu_task))
    cp = timed(processes(cpu_task))
    print(f"{'CPU-bound':22} {cs:8.2f}s {ct:8.2f}s {cp:9.2f}s"
          f"   threads x{cs/ct:.2f}, processes x{cs/cp:.2f}")

    is_ = timed(serial(io_task))
    it = timed(threaded(io_task))
    ip = timed(processes(io_task))
    print(f"{'I/O-bound':22} {is_:8.2f}s {it:8.2f}s {ip:9.2f}s"
          f"   threads x{is_/it:.2f}, processes x{is_/ip:.2f}")

    print("\nspeedup > 1 means faster than doing them one after another")

One run on 23 November 2026 printed this. The CPU threads came out at ×0.81, below the eight-run range of 0.98–1.15: that scatter is exactly why the talk quotes means, and why the I/O figure, pinned at about 4, is the one to trust.

The counter the lock protects

Every object carries a count of the references to it. Three more names, and the count goes up by three; the list goes, and the count comes back. This counter is what two threads would race on. Save it as step2_refcount.py and run python step2_refcount.py.

import sys

word = "flask" * 3                # a fresh string object
print(sys.getrefcount(word))      # references to it right now

names = [word, word, word]        # three more references
print(sys.getrefcount(word))

del names                         # the list goes, and its references with it
print(sys.getrefcount(word))

Threads do not speed up Python arithmetic

Four CPU-bound tasks, one after another, then on four threads. Save it as step3_cpu_threads.py and run python step3_cpu_threads.py.

import time
from concurrent.futures import ThreadPoolExecutor


def cpu_task(_):
    total = 0
    for i in range(6_000_000):
        total += i * i
    return total


t0 = time.perf_counter()
for i in range(4):
    cpu_task(i)
serial = time.perf_counter() - t0

t0 = time.perf_counter()
with ThreadPoolExecutor(4) as pool:
    list(pool.map(cpu_task, range(4)))
threads = time.perf_counter() - t0

print(f"serial {serial:.2f} s, 4 threads {threads:.2f} s: x{serial / threads:.2f}")

Processes compute in parallel, at a price

The same CPU-bound tasks on four processes. Note the __main__ guard. Save it as step5_processes.py and run python step5_processes.py.

import time
from concurrent.futures import ProcessPoolExecutor


def cpu_task(_):
    total = 0
    for i in range(6_000_000):
        total += i * i
    return total


if __name__ == "__main__":        # required: each process re-imports this file
    t0 = time.perf_counter()
    for i in range(4):
        cpu_task(i)
    serial = time.perf_counter() - t0

    t0 = time.perf_counter()
    with ProcessPoolExecutor(4) as pool:
        list(pool.map(cpu_task, range(4)))
    processes = time.perf_counter() - t0

    print(f"serial {serial:.2f} s, 4 processes {processes:.2f} s: x{serial / processes:.2f}")
serial 2.13 s, 4 processes 1.20 s: x1.77

The GIL does not protect your data

Four threads each make 2,000 deposits. Between the read and the write there is a call that releases the GIL, as any I/O would. Without your own lock, most of the deposits are lost. Save it as step6_race.py and run python step6_race.py.

import threading
import time

balance = 0
lock = threading.Lock()


def deposit(times):
    global balance
    for _ in range(times):
        current = balance         # read ...
        time.sleep(0)             # ... any I/O here releases the GIL (a log write, a query) ...
        balance = current + 1     # ... and write back a value that may be stale


def safe_deposit(times):
    global balance
    for _ in range(times):
        with lock:                # your own lock makes the read and the write one step
            current = balance
            time.sleep(0)
            balance = current + 1


for work in (deposit, safe_deposit):
    balance = 0
    threads = [threading.Thread(target=work, args=(2_000,)) for _ in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print(f"{work.__name__:12} expected 8000, got {balance}")
deposit      expected 8000, got 2162
safe_deposit expected 8000, got 8000

What you just saw, by hand. The lock is on (1). Every object carries a reference count the lock protects (2). Threads do not speed up Python arithmetic (3), and they nearly perfectly overlap waiting (4). Processes do compute in parallel, at a price (5). And the GIL never protected your data: your own lock does (6).
